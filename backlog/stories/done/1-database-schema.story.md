# 1 — Create the `clients` + `balances` + `conversions` schema and seed the demo clients

| Field | Value |
|---|---|
| Story Points | 5 |
| Priority | Critical |
| Status | Done |

**Story points rationale:** one layer (`persistence`), zero business logic, but three entities instead
of two — every table gets its own surrogate identifier plus a business/natural key, `balances` and
`conversions` both carry a real FK to `clients`, and the seed migration has to join business client
codes to surrogate ids. Still fully specified below (nothing to discover while coding), which is why
this is a 5 and not an 8, but the extra table and the FK-aware seed migration push it past a 3.

---

## User Story

**As a** foreign-exchange service
**I want** a persisted schema with a `clients` identity table, one balance row per client × currency,
and one row per executed conversion, pre-seeded with two demo clients
**So that** conversions can be run out of the box against real starting balances, `CLIENT_NOT_FOUND` and
`BALANCE_NOT_FOUND` are two distinct, directly-checkable conditions (REQ-8), and the columns REQ-6
(atomic debit/credit), REQ-9 (concurrency), REQ-10 (`Idempotency-Key`) and REQ-11 (`BigDecimal` money
with explicit scale) will build on are decided up front.

---

## Context

**Current behavior:** there is no schema at all. `src/main/java/zetta/foreignexchange/persistence/`
contains only empty `entity/`, `enumeration/`, `mapper/` and `repository/` packages;
`src/main/resources/db/migration/` is empty; `application.yaml` has no `spring.datasource`,
`spring.jpa` or `spring.flyway` keys. Nothing can be persisted or read.

**Required behavior:** starting the application against Postgres applies Flyway migrations that create
`clients`, `balances` and `conversions` with their constraints, indices and foreign keys, and insert the
two demo clients with their opening balances. `ClientEntity`, `BalanceEntity` and `ConversionEntity` map
onto those tables exactly, validated at startup (`ddl-auto: validate`).

**Why a `clients` table, not just two tables:** a client's existence must be checkable independently of
whether it happens to hold any balance — that is exactly the distinction the assignment draws between
`CLIENT_NOT_FOUND` (unknown client) and `BALANCE_NOT_FOUND` (known client, no balance in that currency).
Deriving "client exists" from "has at least one balance row" works only by coincidence of this
assignment's seed-only scope; an explicit `clients` table makes it a direct, first-class check instead.
This is unrelated to the "no ledger/journal model" non-goal — a ledger is about recording individual
balance-changing entries, which is still correctly out of scope; `clients` is just an identity table with
no behavior.

**Why every table has its own surrogate id:** internal database identifiers are never exposed to callers
and never reused as another table's identity. `clients.id`, `balances.id` and `conversions.id` are each
an independent `BIGINT GENERATED BY DEFAULT AS IDENTITY` surrogate key. Business/natural identifiers
(`clients.client_id`, the caller-facing string like `CLIENT-001`; `conversions.transaction_id`, the UUID
returned to the caller) are separate, uniquely-constrained columns — never the primary key.

**Why this is Seq 1:** every later story reads or writes these tables, and their column shapes flow
straight through to the domain models, DTOs and mappers built in Seq 2, 4, 7 and 8. Deciding the columns,
the relationships, the locking column, the idempotency constraint and the history indices once, up front,
is cheaper than retrofitting them onto an implemented `POST /conversions`.

**Grading axis:** correctness (money precision, idempotency and concurrency columns exist before the
logic that needs them) and production sense (schema owned by versioned migrations, never by
`ddl-auto: update`; access paths backed by explicit indices; referential integrity enforced by real FKs).

## Scope

### In Scope

- [ ] `ClientEntity` — JPA entity for `clients`: surrogate `id` (`Long`, `IDENTITY`), unique `client_id`
      (business identifier, e.g. `CLIENT-001`), `createdAt`
- [ ] `BalanceEntity` — JPA entity for `balances`: surrogate `id`, `@ManyToOne` to `ClientEntity`
      (unidirectional, no back-collection), `currency`, `amount`, `@Version` optimistic-lock column,
      `createdAt`/`updatedAt`, unique constraint on `(client_id, currency)`
- [ ] `ConversionEntity` — JPA entity for `conversions`: surrogate `id`, `@ManyToOne` to `ClientEntity`
      (unidirectional), unique `transactionId` (`UUID`, assigned by the application — not the primary
      key), source/target currency + amount, `rate`, nullable `idempotencyKey`, `createdAt`
- [ ] Relationship decisions, recorded in this story:
  - `balances.client_id` and `conversions.client_id` are real foreign keys to `clients.id`
  - **No relationship between `balances` and `conversions`** — a single conversion touches *two*
    balance rows for the same client (source-currency debited, target-currency credited), so a single
    FK from a conversion to one balance row cannot describe it; a proper model would need a join/journal
    table, and a full ledger model is an explicit Non-Goal (`backlog/BACKLOG.md`)
- [ ] Money/rate column precision and scale, identical in the DDL and in the entity `@Column(precision,
      scale)`: `NUMERIC(19,4)` for money, `NUMERIC(19,8)` for `rate`
- [ ] ISO-4217 shape enforced at the database layer with a `CHECK` constraint on every currency column
      (`^[A-Z]{3}$`) — REST-layer validation is added later (Seq 9/REQ-14); this is the persistence-layer
      half, requested explicitly for this story
- [ ] `V1__create_clients_balances_and_conversions.sql` — all three tables, constraints, FKs and
      indices, written idempotently (`CREATE TABLE IF NOT EXISTS`, `CREATE [UNIQUE] INDEX IF NOT EXISTS`)
- [ ] `V2__seed_demo_clients_and_balances.sql` — the two demo clients and their three balance rows,
      re-runnable (`ON CONFLICT DO NOTHING`)
- [ ] Bare `ClientRepository`, `BalanceRepository`, `ConversionRepository` (`extends JpaRepository`,
      **no** custom query methods) — the minimum needed to persist and read entities in this story's tests
- [ ] Baseline `spring.jpa` / `spring.flyway` / `spring.data.rest` configuration in `application.yaml`,
      with `spring.jpa.hibernate.ddl-auto: validate`

### Out of Scope

- Service interfaces or implementations (`core/service/*` skeletons exist and stay untouched)
- MapStruct mappers, entity ↔ domain models, and the MapStruct dependency itself (not on the classpath;

- Derived/custom repository query methods such as `findByClientClientInOrderByCurrencyAsc` or history filtering — Seq 2, 4/5 and
  8 add them next to the code that calls them
- REST-layer ISO-4217 / positive-amount / non-blank-client-id validation (`@Valid`, custom validators) —

- Controllers, DTOs, error codes, `@ControllerAdvice`
- Optimistic-lock conflict detection, retry or 409/422 translation — this story only adds the `@Version`

- Docker/compose changes for the production datasource — Seq 11

## Acceptance Criteria

- [ ] Running the application (or an integration test) against an empty Postgres applies `V1` and `V2`
      and leaves `clients`, `balances` and `conversions` present, with Hibernate schema validation passing
      (`ddl-auto: validate`) — entities and DDL agree on every column name and type
- [ ] After migration, `clients` contains exactly `CLIENT-001` and `CLIENT-002`
- [ ] After migration, `balances` contains exactly three rows, each correctly linked via FK to its
      client: `CLIENT-001` → `10000.0000 USD`, `CLIENT-001` → `8000.0000 EUR`, `CLIENT-002` →
      `5000.0000 GBP`
- [ ] Inserting a second `balances` row with the same `(client_id, currency)` pair as an existing row is
      rejected by the unique constraint
- [ ] Inserting a `balances` or `conversions` row that references a non-existent `clients.id` is
      rejected by the foreign key constraint
- [ ] `BalanceEntity` exposes a `@Version` field; loading a row, having a second persistence context
      update it, and then flushing the stale copy raises an optimistic-lock failure
- [ ] Inserting a currency value that is not exactly three uppercase letters (e.g. `usd`, `US`, `USDD`)
      into any currency column is rejected by the `CHECK` constraint
- [ ] Inserting two `conversions` rows with the same `(client_id, idempotency_key)` is rejected, while
      any number of rows with a `NULL` `idempotency_key` for the same client are accepted
- [ ] Inserting two `conversions` rows with the same `transaction_id` is rejected
- [ ] Money and rate values survive a save/load round trip with their declared scale intact (e.g.
      `10000.0000` reads back as scale 4, not truncated or rescaled)
- [ ] `GET /clientBalances`, `/balances`, `/conversions`, `/clients` (Spring Data REST auto-exposure) are
      **not** served — see R1 in Implementation Notes
- [ ] Re-running `V1` and `V2` against a database that already has them applied performs no destructive
      change and raises no error (idempotent, backward-compatible migrations)

### Existing Pattern Reference

There is no existing entity, repository or migration to copy — this story establishes those patterns.
The one pattern that does exist is how a test gets a real Postgres, in
`src/test/java/zetta/foreignexchange/TestcontainersConfiguration.java`:

```java

    @Bean
    @ServiceConnection
    PostgreSQLContainer postgresContainer() {
        return new PostgreSQLContainer(DockerImageName.parse("postgres:latest"));
    }
}
```

Reuse it rather than starting containers by hand; `@ServiceConnection` supplies the datasource so
Flyway and JPA run against the container exactly as they would in production. Tests in this story are
shaped as:

```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Import(TestcontainersConfiguration.class)
class BalanceEntityIntegrationTest { /* ... */ }
```

`@AutoConfigureTestDatabase(replace = NONE)` is required — without it Spring swaps in an embedded
database and the Postgres-specific DDL (partial unique index, `NUMERIC` precision, `CHECK` constraints)
is never exercised.

## Implementation Notes

### Table: `clients`

| Column | Type | Notes |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | surrogate primary key — never exposed to callers |
| `client_id` | `VARCHAR(64) NOT NULL` | caller-supplied business identifier, e.g. `CLIENT-001` |
| `created_at` | `TIMESTAMPTZ NOT NULL` | assigned in Java via `@CreationTimestamp` (see R2) |

Constraint: `UNIQUE (client_id)`.

### Table: `balances`

| Column | Type | Notes |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | surrogate primary key |
| `client_id` | `BIGINT NOT NULL REFERENCES clients (id)` | FK to `clients.id` — mapped in Java as a `@ManyToOne ClientEntity client`, not a raw `Long` field |
| `currency` | `VARCHAR(3) NOT NULL` | ISO-4217 alpha code |
| `amount` | `NUMERIC(19,4) NOT NULL` | the client's holding in that currency |
| `version` | `BIGINT NOT NULL DEFAULT 0` | `@Version` optimistic lock |
| `created_at` | `TIMESTAMPTZ NOT NULL` | `@CreationTimestamp` |
| `updated_at` | `TIMESTAMPTZ NOT NULL` | `@UpdateTimestamp` |

Constraints: `UNIQUE (client_id, currency)` — the "one row per client × currency" rule; this composite
unique constraint's leading column also serves `client_id`-only lookups, so no separate index is needed.
`CHECK (currency ~ '^[A-Z]{3}$')`. `CHECK (amount >= 0)` — makes a negative balance structurally
impossible rather than merely unlikely (REQ-9 is the most heavily graded correctness property; this is a
one-line, zero-cost backstop for it).

### Table: `conversions`

| Column | Type | Notes |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | surrogate primary key |
| `transaction_id` | `UUID NOT NULL` | business identifier returned to the caller and accepted by `GET /conversions?transactionId=`; assigned by the application (`UUID.randomUUID()`), not database-generated, and is **not** the primary key |
| `client_id` | `BIGINT NOT NULL REFERENCES clients (id)` | FK to `clients.id`, mapped as `@ManyToOne ClientEntity client` |
| `source_currency` | `VARCHAR(3) NOT NULL` | |
| `source_amount` | `NUMERIC(19,4) NOT NULL` | amount debited |
| `target_currency` | `VARCHAR(3) NOT NULL` | |
| `target_amount` | `NUMERIC(19,4) NOT NULL` | amount credited |
| `rate` | `NUMERIC(19,8) NOT NULL` | rate applied at conversion time — frozen here forever; a later change in the live rate must never alter history |
| `idempotency_key` | `VARCHAR(128) NULL` | from the optional `Idempotency-Key` header |
| `created_at` | `TIMESTAMPTZ NOT NULL` | `@CreationTimestamp`; also the column the `date` history filter targets |

Constraints and indices:
- `UNIQUE (transaction_id)` — lookup by `transactionId` is a single-row hit
- `CHECK (source_currency ~ '^[A-Z]{3}$')`, `CHECK (target_currency ~ '^[A-Z]{3}$')`
- `CHECK (source_amount > 0 AND target_amount > 0 AND rate > 0)`
- `CREATE UNIQUE INDEX conversions_client_idempotency_key ON conversions (client_id, idempotency_key)
  WHERE idempotency_key IS NOT NULL` — a **partial** unique index: the database, not the application,
  guarantees one conversion per key per client, while conversions sent without a key are unconstrained
- `INDEX (client_id, created_at DESC)` — `GET /conversions` filters by `clientId` and orders/filters by
  date together; the leading column also serves a `clientId`-only filter
- `INDEX (created_at)` — for a date-only filter with no `clientId`

**No relationship between `balances` and `conversions`.** A single conversion updates two balance rows
for the same client (the source-currency row debited, the target-currency row credited) — a single FK
from a conversion to *one* balance row cannot describe that. Modelling it properly would require a
join/journal table, which is a full ledger model and an explicit Non-Goal. `conversions` therefore only
carries the `client_id` FK to `clients`; the individual `balances` rows it affected are not recorded.
Consequence to carry into Seq 4/13 (README trade-offs): a conversion row is an immutable historical
snapshot — it stores its own source/target currency, amounts and rate — precisely so it never needs to
reference a `balances` row (which is mutable current state) to remain meaningful.

**Why `@Version` optimistic locking, not a pessimistic row lock:** single-instance service, rare
contention in the common case — optimistic locking costs nothing when there is none, whereas
`SELECT ... FOR UPDATE` serializes every conversion for a client whether or not anyone else is
converting. One column, one annotation (KISS), and it makes the conflict explicit and testable at the
application boundary. **This story adds only the column and the annotation** — detecting
`OptimisticLockingFailureException`, retrying, and mapping it to a response is Seq 6.

**Money precision:** `NUMERIC(19,4)` for all balance and amount columns (4 decimal places covers every
ISO-4217 minor unit, including 3-decimal currencies like BHD/KWD, with a guard digit); `NUMERIC(19,8)`
for `rate` (provider rates carry more significant decimals than money does; rounding the rate before
applying it would bias the result). Entities declare `BigDecimal` with matching
`@Column(precision, scale)` — never `double`/`float` (REQ-11). The rounding **mode** used when computing
a target amount is a `core` concern (Seq 4); this story only guarantees the stored scale. Postgres
silently rounds any `BigDecimal` with a larger scale on insert with no error raised, so Seq 4 must
`setScale(4, RoundingMode.HALF_UP)` (or the chosen mode) *before* persisting, not rely on the column.

**Currency as `String`, not an enum:** the `persistence/enumeration` package exists but stays empty
here. Rates come from Frankfurter for any ISO-4217 code; hard-coding an enum of supported currencies
would make the schema the thing that limits the service. Full ISO-4217 semantic validation belongs at the
REST boundary (Seq 9/REQ-14); this story's `CHECK` constraint only enforces the *shape* (three uppercase
letters), which is what stops a case-sensitivity or malformed-value bug from ever corrupting a row,
regardless of what the application layer does.

**Every table's own surrogate id:** `clients.id`, `balances.id`, `conversions.id` are each an
independent `BIGINT GENERATED BY DEFAULT AS IDENTITY`. No table borrows another's id as its own primary
key, and no internal id is exposed through the API — the caller only ever sees `client_id` (as supplied
by them) and `transaction_id` (as generated for them). Repositories are typed
`JpaRepository<XxxEntity, Long>` accordingly (not `<ConversionEntity, UUID>`).

**Migration discipline:** `V1` creates, `V2` seeds — kept separate so the seed can be replaced per
environment without touching the DDL version. Both use `IF NOT EXISTS` / `ON CONFLICT DO NOTHING` so
re-application is safe. `V2`'s balance insert joins the seed values to `clients` by business `client_id`
to resolve the surrogate FK:

```sql
INSERT INTO balances (client_id, currency, amount, created_at, updated_at)
SELECT c.id, v.currency, v.amount, now(), now()
FROM clients c
JOIN (VALUES
    ('CLIENT-001', 'USD', 10000.0000),
    ('CLIENT-001', 'EUR', 8000.0000),
    ('CLIENT-002', 'GBP', 5000.0000)
) AS v(client_id, currency, amount) ON v.client_id = c.client_id
ON CONFLICT (client_id, currency) DO NOTHING;
```

`ddl-auto: validate` (never `update`) — Flyway is the only thing that changes schema; `validate` turns
any entity/DDL drift into a startup failure instead of a silent runtime error. This does not contradict
the assignment's "do not rely on `ddl-auto=update`" instruction — `validate` generates no DDL at all, it
only compares Hibernate's view of the schema against what Flyway already built.

**Timestamps — `OffsetDateTime`, never `LocalDateTime`, assigned by Hibernate, not the database
default (R2):** two traps to avoid: (1) Hibernate maps `LocalDateTime` to `timestamp without time zone`,
which fails `ddl-auto: validate` against a `TIMESTAMPTZ` column — use `OffsetDateTime`. (2) Hibernate
includes every mapped column in the `INSERT`, so an unset `createdAt` is written as an explicit `NULL`
and any DB-side `DEFAULT now()` is never reached — populate via `@CreationTimestamp`/`@UpdateTimestamp`.
This only applies to rows persisted through Hibernate; `V2`'s raw-SQL seed insert can use `now()`
directly since no entity lifecycle is involved there.

**R1 — Spring Data REST must not auto-expose these repositories.** `spring-boot-starter-data-rest` is on
the classpath (`pom.xml`). Its default detection strategy exposes every public `JpaRepository` as an
unauthenticated HTTP CRUD resource. The moment `ClientRepository`, `BalanceRepository` and
`ConversionRepository` exist, the app would serve unauthenticated `GET/POST/PATCH/DELETE /clients`,
`/balances`, `/conversions` — arbitrary balance mutation bypassing the transaction, the `@Version` check,
the insufficient-funds rule and the idempotency key. It does not collide with the hand-written
controllers (mapped under `/api/v1`), which makes it silent rather than obvious. **Required in this
story:**

```yaml
spring:
  data:
    rest:
      detection-strategy: annotated
```

plus a test asserting the auto-exposed routes are gone (Red/Green 9 above). Removing the
`spring-boot-starter-data-rest` dependency outright would be the cleaner long-term fix, but that is a
dependency removal and needs explicit user approval — raise it, do not do it unilaterally.

**Migration immutability once applied (R4):** Flyway checksums each migration file the first time it
runs it against a database. Editing `V1`/`V2` after they've been applied to the local `docker-compose`
Postgres (whose volume persists across restarts) trips a checksum mismatch on the next boot and the app
refuses to start. Testcontainers gives a fresh database every run, so this never bites there. While
iterating locally against `docker-compose`, run `docker compose down -v` between edits to reset the
volume. Once this story closes, `V1`/`V2` are frozen forever — any future schema change is a new,
additive `V3__...sql`.

**Lombok** is on the classpath; entities may use `@Getter`/`@Setter`/`@NoArgsConstructor`. Entities are
mutable JPA classes, so they are **classes, not records** (`.claude/CLAUDE.md` Record vs Class). Avoid
`@Data`/`@EqualsAndHashCode` on entities — identity-based equality plus a lazy `hashCode` over all
fields (and, with a `@ManyToOne`, over a lazy proxy) is a known JPA trap.

**Test technique for the two trickiest acceptance criteria:**
- Constraint violations: assert on `saveAndFlush(...)`, not `save(...)` — `@DataJpaTest` defers the
  flush to commit, which never happens under rollback. One violation assertion per test method; the
  persistence context is unusable after one fires.
- Optimistic lock: inside a single `@DataJpaTest` transaction the persistence context returns the same
  managed instance for repeated `findById` calls, so a stale copy can't be produced that way. Load the
  entity, bump the row out of band with a native `UPDATE balances SET version = version + 1 WHERE
  id = :id`, then mutate and flush the now-stale managed instance.

## Resolved Design Decisions (settled in conversation before implementation)

These were explicitly discussed and agreed before any code was written, superseding earlier drafts of
this story:

1. **Add a `clients` table** with `@ManyToOne` FKs from `balances` and `conversions` — not a two-table
   design. Rationale above (Context section).
2. **Every table gets its own independent surrogate `Long`/`IDENTITY` primary key** — `client_id` and
   `transaction_id` are business/natural keys with their own unique constraints, never the `@Id`.
   Internal database identifiers are never exposed to callers.
3. **`BigDecimal` (Java) and `NUMERIC` (Postgres) are the same concept in two languages**, not
   competing choices — `@Column(precision, scale)` on a `BigDecimal` field is what generates the
   `NUMERIC(p,s)` DDL. This is the only correct mapping for money; it is not an open question.
4. **Currency `CHECK (col ~ '^[A-Z]{3}$')` constraints are in scope for this story** (persistence layer);
   the equivalent REST-layer validation is deferred to Seq 9/REQ-14, not skipped.
5. **`ddl-auto: validate` is compliant with "do not rely on `ddl-auto=update`"** — it performs a
   read-only comparison at startup and generates no DDL; Flyway remains the only schema-changing
   mechanism.
6. **`docker compose down -v` is the agreed workflow** for resetting the local Postgres volume while
   iterating on `V1`/`V2` during this story's Red/Green cycles.
